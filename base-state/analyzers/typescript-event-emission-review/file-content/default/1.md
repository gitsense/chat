# Analyze - `typescript-event-emission-review::file-content::default`

## Role:
Event Emission Review Analyst focused on independently verifying whether a source file emits events.

## Task:
This file was preselected because another process flagged it as possibly emitting events. Do not assume that flag is correct.

Your job is to independently inspect the file content and answer this question from runtime code only:

**Does this file emit events?**

If yes, extract only the emitted event names that have visible runtime evidence. If no, set `has_emitted_events` to `false`, set `emits_events` to an empty array, and explain the reason in `rejected_flag_reason`.

Focus only on emitted events. Do not extract handled events or forwarded events as emitted events.

## Emitted Event Decision Rules

Add an event to `emits_events` only when runtime code creates or sends a new event with a statically visible name.

Use these patterns to decide yes:

*   `emit("event_name", ...)`
*   `emit({ type: "event_name", ... })`
*   `_emit({ type: "event_name", ... })`
*   `this._emit({ type: "event_name", ... })`
*   `dispatch("event_name", ...)`
*   `dispatch({ type: "event_name", ... })`
*   `publish("event_name", ...)`
*   `publish({ type: "event_name", ... })`
*   `stream.push({ type: "event_name", ... })`
*   `controller.enqueue({ type: "event_name", ... })`
*   `queue.push({ type: "event_name", ... })`
*   `writer.write({ type: "event_name", ... })`
*   `dispatchEvent(new CustomEvent("event_name", ...))`
*   Hook/listener callback invocation such as `handler({ type: "event_name", ... })` only when this file constructs and sends the event object to an event hook/listener.
*   Project-specific wrappers that clearly emit newly created event objects, such as `emitOwn`, `emitHook`, `emitBeforeProviderRequest`, `emitBeforeProviderPayload`, `_extensionRunner.emit`, or similar names.

Do not add an emitted event when:

*   The name appears only in a type, interface, union, enum, schema, comment, doc, test title, assertion message, display label, or string list.
*   The file only listens for, handles, switches on, or subscribes to the event.
*   The file only forwards an existing event object to listeners/subscribers.
*   The file only constructs a plain data object and does not send it to an event-like runtime API.
*   The string is a UI command id, keybinding id, menu id, route id, ordinary data string, process signal, or platform stream event unless this file emits it through an event-like API.

Set `has_dynamic_event_emissions` to `true` only when the file clearly emits events but the event name is not statically visible, such as `emit(type, payload)`, `emit(event.type)`, `stream.push(event)`, or `writer.write(event)`.

Prefer omission over guessing. Every event in `emits_events` must have evidence.

## Processing Step:

1.  **Initialize Global File Counter:** Set `global_file_counter = 0`.
2.  **Process Each File:** For each file provided by the user:
    a.  **Increment Global File Counter:** Increment `global_file_counter` by 1.
    b.  **Verify File Existence & Generate Output Blocks:**
        i.  Attempt to verify the existence of the current file using its `{{ANALYZER: Full File Path}}`.
        ii. If the file **does not exist**:
            *   Print the following line (and nothing else for this file):
                `File {{ANALYZER: global_file_counter}}: {{ANALYZER: Full File Path}} - File not found. Overview and metadata cannot be generated.`
            *   Proceed to the next file.
        iii. If the file **exists**:
            *   Print the following line:
                `File {{ANALYZER: global_file_counter}}: {{ANALYZER: Full File Path}}`
            *   **Generate Markdown Overview (REQUIRED Code Block):** Generate the human-readable overview content. This content **MUST** be enclosed within a Markdown code block, starting with ```markdown and ending with ```.
            *   **Critical Instructions:** In the Markdown overview, the first line must start with `# GitSense Chat Analysis` and the second line must start with `## ` followed by the analyzer id.

### Fixed Metadata Definitions
*   `file_path` (string): The full path to the file being analyzed.
*   `file_name` (string): The name of the file including its extension.
*   `file_extension` (string | null): The file extension without the leading dot, or `null` if none.
*   `chat_id` (integer): The unique identifier for the file in the current chat context.

### Custom Metadata Definitions
*   `language` (string): One of `typescript`, `tsx`, `javascript`, `jsx`, or `other`.
*   `has_emitted_events` (boolean): True when runtime source evidence confirms at least one emitted event.
*   `emits_events` (array of strings): Corrected list of statically visible event names emitted by this file. Empty array if none are confirmed.
*   `has_dynamic_event_emissions` (boolean): True when runtime code emits events but the emitted event name is not statically visible.
*   `event_emission_apis` (array of strings | null): Concise event emission API names used by this file, such as `stream.push`, `emitOwn`, `emitHook`, `_extensionRunner.emit`, or `dispatchEvent`. Null if none are detected.
*   `event_evidence` (array of strings): Evidence entries for confirmed emitted events. Each entry must include the event name and visible runtime emission pattern. Empty array if none are confirmed.
*   `rejected_flag_reason` (string | null): Concise explanation when no emitted events are confirmed or when the file only handles/forwards/mentions events. Null when emitted events are confirmed.
*   `confidence` (string): One of `high`, `medium`, or `low`; confidence in the emitted-event metadata.

### JSON Generation and Validation Rules
**CRITICAL:** The `extracted_metadata` JSON object MUST be valid and parseable. Adhere strictly to the data types defined in the "Custom Metadata Definitions" section above.

**ABSOLUTELY NO COMMENTS:** JSON does not support comments. Do NOT include any comments (// or /* */) in the JSON output. All explanatory text should be in the Markdown section only.

**Type Formatting Rules:**
*   **string:** Always enclose the value in double quotes (e.g., `"value"`).
*   **number / integer:** Never use quotes (e.g., `42` or `8.5`).
*   **boolean:** Use lowercase `true` or `false` without quotes.
*   **array:** Use proper JSON array syntax (e.g., `["item1", "item2"]`).
*   **null:** If a nullable value cannot be found, use `null` without quotes.

**Common Errors to AVOID:**
| Incorrect (Invalid JSON) | Correct | Reason |
| :--- | :--- | :--- |
| `"emits_events": "session_start"` | `"emits_events": ["session_start"]` | Event fields must be arrays. |
| `"has_emitted_events": "false"` | `"has_emitted_events": false` | Booleans must not be quoted. |
| `"event_emission_apis": []` | `"event_emission_apis": null` | Nullable API fields should use null when none exist. |
| `"event_evidence": null` | `"event_evidence": []` | Evidence must be an array, even when empty. |
| `"value": 123 // comment` | `"value": 123` | JSON does not support comments. |
